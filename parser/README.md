SQL to Relational Algebra Parser
=================================

This parser takes a SQL SELECT query as input and outputs a relational algebra
expression tree in JSON format. It is built using Flex (lexer) and Bison (parser).


Files
------

sql_parser.y      Bison grammar file. Contains the full grammar, all data structure
                  definitions, helper functions, and the main() entry point.

sql_tokeniser.l   Flex lexer file. Tokenises the SQL input and returns token codes
                  to the parser.

tokens.h          Reference-only token definitions. Not included in the build.
                  The actual token definitions come from y.tab.h generated by Bison.

ref.y, ref.l      Reference implementations provided with the assignment. Not part
ref.h             of the build.


Build Instructions
-------------------

Requires: bison, flex, g++

Run the following commands in the directory containing the source files:

    bison -d -o y.tab.c sql_parser.y
    flex -o lex.yy.c sql_tokeniser.l
    g++ -o sql_parser y.tab.c lex.yy.c -lfl

This produces the executable sql_parser.


How to Run
-----------

The parser reads from standard input by default:

    echo "SELECT e.name FROM employees e WHERE e.salary > 50000" | ./sql_parser

You can also pass a file containing the query:

    ./sql_parser query.txt

A query file should contain exactly one SQL query. The query can span multiple
lines. No semicolon is needed at the end.


Input Format
-------------

The parser accepts a subset of SQL with the following structure:

    SELECT <column_list>
    FROM <table_or_join>
    [WHERE <condition>]
    [GROUP BY <column_list>]
    [HAVING <condition>]

Column references must always be qualified with a table name or alias:

    table.attribute        e.g.  e.name
    table.*                e.g.  e.*
    *                      selects all columns

Table references support optional aliases (AS keyword is optional):

    tablename
    tablename AS alias
    tablename alias

Joins use explicit JOIN ... ON syntax:

    FROM t1 JOIN t2 ON t1.col = t2.col

Subqueries in FROM must have an alias:

    FROM (SELECT ...) AS alias

Conditions support AND, OR, NOT, and parentheses for grouping. Comparison
operators are: =, <, >, <=, >=, <>

Literals supported: integers, floats, single-quoted strings.


Output Format
--------------

Output is pretty-printed, multi-line JSON representing the relational algebra tree.
Each node has a "type" field. The tree is built bottom-up, so the innermost
node is the base relation and the outermost is the final projection.

Node types:

    project         Final column projection. Fields: columns, input.
    select          Tuple selection (WHERE). Fields: condition, input.
    join            Natural join on condition. Fields: condition, left, right.
    groupby         Grouping. Fields: group_cols, having (null if no HAVING), input.
    subquery        Inline view. Fields: alias, query.
    base_relation   A table reference. Fields: tables (list of name + optional alias).

Condition node types: EQ, LT, GT, LE, GE, NE, AND, OR, NOT.

Comparison nodes have fields: left (table+attr), right (typed literal or column).
Literal types: "int", "float", "string", "column".


Sample Inputs and Outputs
--------------------------

--- Sample 1: Simple SELECT with WHERE ---

Input:
    SELECT e.name, e.salary FROM employees e WHERE e.salary > 50000

Output:
    {
        "type": "project",
        "columns": [{"table": "e", "attr": "name"}, {"table": "e", "attr": "salary"}],
        "input": {
            "type": "select",
            "condition": {
                "type": "GT",
                "left": {"table": "e", "attr": "salary"},
                "right": {"type": "int", "value": 50000}
            },
            "input": {
                "type": "base_relation",
                "tables": [{"name": "employees", "alias": "e"}]
            }
        }
    }


--- Sample 2: JOIN without WHERE ---

Input:
    SELECT e.name, d.dept_name
    FROM employees e JOIN departments d ON e.dept_id = d.id

Output:
    {
        "type": "project",
        "columns": [{"table": "e", "attr": "name"}, {"table": "d", "attr": "dept_name"}],
        "input": {
            "type": "join",
            "condition": {
                "type": "EQ",
                "left": {"table": "e", "attr": "dept_id"},
                "right": {"type": "column", "table": "d", "attr": "id"}
            },
            "left": {
                "type": "base_relation",
                "tables": [{"name": "employees", "alias": "e"}]
            },
            "right": {
                "type": "base_relation",
                "tables": [{"name": "departments", "alias": "d"}]
            }
        }
    }


--- Sample 3: WHERE with AND and string literal ---

Input:
    SELECT e.name FROM employees e
    WHERE e.age > 30 AND e.dept = 'engineering'

Output:
    {
        "type": "project",
        "columns": [{"table": "e", "attr": "name"}],
        "input": {
            "type": "select",
            "condition": {
                "type": "AND",
                "left": {
                    "type": "GT",
                    "left": {"table": "e", "attr": "age"},
                    "right": {"type": "int", "value": 30}
                },
                "right": {
                    "type": "EQ",
                    "left": {"table": "e", "attr": "dept"},
                    "right": {"type": "string", "value": "engineering"}
                }
            },
            "input": {
                "type": "base_relation",
                "tables": [{"name": "employees", "alias": "e"}]
            }
        }
    }


--- Sample 4: GROUP BY with HAVING ---

Input:
    SELECT e.dept_id FROM employees e
    GROUP BY e.dept_id HAVING e.salary > 40000

Output:
    {
        "type": "project",
        "columns": [{"table": "e", "attr": "dept_id"}],
        "input": {
            "type": "groupby",
            "group_cols": [{"table": "e", "attr": "dept_id"}],
            "having": {
                "type": "GT",
                "left": {"table": "e", "attr": "salary"},
                "right": {"type": "int", "value": 40000}
            },
            "input": {
                "type": "base_relation",
                "tables": [{"name": "employees", "alias": "e"}]
            }
        }
    }


--- Sample 5: Subquery in FROM ---

Input:
    SELECT s.name FROM
    (SELECT e.name, e.dept FROM employees e WHERE e.active = 1) AS s
    WHERE s.dept = 2

Output:
    {
        "type": "project",
        "columns": [{"table": "s", "attr": "name"}],
        "input": {
            "type": "select",
            "condition": {
                "type": "EQ",
                "left": {"table": "s", "attr": "dept"},
                "right": {"type": "int", "value": 2}
            },
            "input": {
                "type": "subquery",
                "alias": "s",
                "query": {
                    "type": "project",
                    "columns": [{"table": "e", "attr": "name"}, {"table": "e", "attr": "dept"}],
                    "input": {
                        "type": "select",
                        "condition": {
                            "type": "EQ",
                            "left": {"table": "e", "attr": "active"},
                            "right": {"type": "int", "value": 1}
                        },
                        "input": {
                            "type": "base_relation",
                            "tables": [{"name": "employees", "alias": "e"}]
                        }
                    }
                }
            }
        }
    }


Error Handling
---------------

If the input does not match the grammar, the parser prints an error to stderr:

    Error: syntax error

and produces no output on stdout. Invalid characters in the input are reported
character by character to stderr but parsing continues.


Limitations
------------

- Columns in SELECT and WHERE must always be qualified as table.attribute.
  Bare attribute names without a table prefix are not supported.
- Only inner joins (JOIN ... ON) are supported. LEFT/RIGHT/FULL OUTER JOIN
  and CROSS JOIN are not handled.
- Aggregate functions (COUNT, SUM, AVG, etc.) are not parsed; they would
  appear as unrecognised identifiers.
- Only one query per input is accepted. Multiple statements are not supported.
- ORDER BY and LIMIT are not supported.
